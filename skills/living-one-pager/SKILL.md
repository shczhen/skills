# Living One-pager

Keep a shared, useful account of a product or capability so its maker and someone preparing content can understand and explain it. One person can do both. Collect the facts and materials that make the product understandable, write a coherent overview, and maintain it as the product develops, launches, gets used, and changes. Product development stays in the user's existing workflow.

## Start with the product

Find the product or capability being explained and its existing page, sources, and storage agreement. Read the conversation and supplied files or accessible links before asking for information. For a specified agent session, use the host's supported history reader; if unavailable, request an accessible export. Use the work already done, whether it is an idea, a working product, or a released capability.

Reuse the existing product entry. Development rounds, new goals, releases, and new conversations update that entry. Create a separate linked page only when there is a distinct product or capability that actually needs its own explanation. Preserve existing identifiers, paths, and links.

## Write a product overview people can use

Adapt [the versioned template](assets/one-pager.md) to the actual product. Establish:

- What it is, its users and situations, the problem, and its value.
- What it does, representative use cases, and how its components fit together when that helps.
- How someone can experience it: entry points, examples, usage steps, demos, and current limits.
- What supports its claims: results, user feedback, comparisons, and their conditions.
- Which content materials exist, what they can be used for, and the useful missing input.

Write the explanation from available facts rather than filling a questionnaire. An idea may support only the user problem and intended value; leave implementation and results unverified. With an existing product, explain the actual product before discussing its progress or next action. Omit irrelevant sections and keep detailed evidence and discussions behind links.

Use [source and material guidance](references/workflow.md) when taking in conversations, linked assets, or several versions of a product description. Ask for the next existing example or factual clarification that changes the explanation; collecting a missing input does not assign its development to this skill.

## Keep the explanation and materials aligned

Read the current page and relevant sources before changing it. Put a new capability, availability change, result, or decision into the part of the product explanation it changes. Retain valid earlier facts and important history. Show which existing handouts, blogs, demos, or other materials need attention; edit those materials when they are included in the request and accessible. State any destination that could not be updated.

Tie claims to sources and conditions. Distinguish intended value from observed results, user reports from independent verification, and suggestions from decisions. Describe missing evidence as **not provided / unknown**. Reserve **not started / unpublished / no feedback** for a source that explicitly establishes that absence: a next goal or draft label is insufficient. A new document does not reset product progress. When descriptions disagree, compare their scope and conditions and surface the unresolved difference; do not choose a number or release status without evidence.

Preserve relevant original material and substantive user and assistant discussion within the storage agreement, with roles and coverage clear. Summarize changes on the main page and link longer history. See [update guidance](references/updates.md) for continuity, material changes, and repeated input.

## Agree storage once

Reuse an explicit project agreement. Otherwise present these defaults together, with the actual resolved destination, for acceptance or adjustment:

- **Where:** local current project; reuse its existing record directory, otherwise `./work-items/<product-id>/one-pager.md`.
- **What:** the product's related facts, progress, materials, discussions, decisions, feedback, data, and available original conversations and attachments, with sources.
- **How much:** as complete as possible, retaining context and history without automatic truncation or cleanup.

Provide the useful product synthesis while saving awaits a choice. Loading a local skill or continuing the discussion is not accepting storage. After defaults are shown, an explicit request to create/save can accept them; an existing clear choice needs no repeated confirmation. Use another local path, Gist, document/wiki, or combined destinations when selected and available. A supplied link for reading is not permission to overwrite it. Keep the agreement in the existing project entry or linked history so setup does not dominate the product overview.

## Version the page and upgrade deliberately

Skill version is `0.3.0`; the main template is `living-one-pager` version `1.0.0`. New pages record the applied template version, their own revision, the skill used, and the document update date. For a wiki, show the same information in a small version line.

Read [version and upgrade guidance](references/versions.md) when creating a versioned page, changing a page, or upgrading an old one. Increment its revision for an actual saved change, add a short changelog entry, and keep a replay/no-op unchanged. The installed skill version and the page's applied template version are independent. An ordinary product update preserves the existing format unless a restructuring/upgrade is requested; updating the skill alone does not migrate user documents.

## Use and improve the material

Lead the reply with the useful product explanation or what changed, the materials ready to use, and the next useful input. Link the page and sources. When requested, use them to prepare a one-sheet, article, demo, or [brief](assets/communication-brief.md); the internal entry and a public one-sheet may share a document or use separate views as needed. Making every content format is not a prerequisite for a good one-pager.

Accept feedback in ordinary language and retain its context. Personal preferences belong in the local template; reusable problems can improve this skill. Use [public-copy guidance](references/public-export.md) when preparing shareable material or a public Issue. Preparing content is separate from publishing or sending it. Keep reviews useful to the actual work, without approval chains or fixed reporting schedules.
